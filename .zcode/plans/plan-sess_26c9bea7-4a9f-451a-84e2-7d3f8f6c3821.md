# 应用集成完整性修复计划（api-assembly 规范方式）

## 审计结论

对照 `specs/component.spec.json`（101 依赖服务/45 foundation feature）分层核查：
- ✅ Cargo 证据层、数据库引导层（`embedded_database_bootstrap.rs`）、契约证据闭包（`gateway:api:validate` 通过，2763 路由）均完整
- ❌ **路由装配层缺 18 个 feature**（`embedded_dependency_routes.rs` 仅 27/45 接线）：rtc, cms, forum, mail, mcp, aiot, agents, promotion, browser, knowledgebase, llm, modelkit, account, catalog, customerservice, gameengine, local-router, manager → 48 个 API surface 运行期 503
- ❌ 这 18 个应用仓库的 assembly 仍是旧式 `ApiAssembly { router }` 形态，不符合 `API_ASSEMBLY_SPEC.md` 的贡献式契约（`ApiAssembly = ApiAssemblyContribution`，六要素齐全）；部分 route crate 缺 `gateway_route_manifest()`；customerservice/manager 的 spec 导出名在 assembly 中不存在

## 规范路径（按 API_ASSEMBLY_SPEC.md §4/§5/§7/§10）

集成必须以各应用仓库的规范 api-assembly 工具链完成：`bootstrap-api-assembly-repo.mjs`（已就位）→ `pnpm api:assembly:materialize`（确定性物化，保留 authored bootstrap）→ `pnpm api:assembly:validate`（只读门禁）→ `audit-api-assembly-workspace.mjs`。网关侧按 §6.2 只做"选择与消费"。

## Phase 1 — 18 个应用仓库规范集成（每仓库独立 commit，分三批）

每仓库统一执行：
1. **Route crate 补齐**：确保 `gateway_mount` 返回可执行 `axum::Router`（多数已有）；缺失 `gateway_route_manifest()` 的按既有模式补齐（rtc/mail/aiot/agents 可用 build.rs 已生成的 `HttpRoute` 数组；cms/forum 从旧式 const 映射；modelkit/account/catalog/gameengine/local-router 从已物化 `sdks/_route-manifests/*.route-manifest.json` / openapi 生成 `http_route_manifest.rs` + `gateway_route_manifest()`，参照 news/mcp 已接线范例）
2. **Bootstrap 升级为贡献式契约**（authored，materialize 会保留）：`pub type ApiAssembly = ApiAssemblyContribution;` + 规范入口 `pub async fn assemble_api_router(context: ApiAssemblyContext) -> Result<ApiAssembly, String>` + 网关族便捷入口 `assemble_api_router_with_pool(pool: DatabasePool)`（进程共享池注入，符合 process-database-pool 契约）；manifest 从各 route crate 的 `gateway_route_manifest()` 收集（`HttpRouteManifest::from_owned_routes`），readiness 用 `DatabasePoolReadinessCheck`/`PgPoolReadinessCheck`；`ApiAssemblyContribution::from_manifest(...)`（无物化 openapi 的仓库）或 `from_openapi_documents(...)`（有物化 openapi 的仓库，如 rtc/cms/mail/mcp/aiot/promotion/knowledgebase/llm/modelkit/account/catalog/customerservice/gameengine/manager）
3. 运行 `pnpm api:assembly:materialize`（重生物化 `assembly-manifest.json`/`generated.rs`）→ `pnpm api:assembly:validate` 必须通过 → `cargo check -p sdkwork-api-<code>-assembly`

批次（按 route crate 成熟度）：
- **批次 A（11）**：promotion、knowledgebase（已贡献式，仅补 `_with_pool` 入口）、mcp、browser、llm、customerservice、manager（后两者含新增 `assemble_api_router_with_pool`，替代 spec 中不存在的旧导出名）、agents、rtc、mail、aiot
- **批次 B（2）**：cms（app/backend route crate 补 manifest，open 已有）、forum（旧式 const 映射）
- **批次 C（5）**：modelkit、account（修空 manifest）、catalog、gameengine、local-router（其 `RuntimeHandle` 由网关侧保留，确认不在网关进程内自行 bind）

特殊处理：browser 同步导出（无需 await）；forum 导出无 Result；promotion/account/catalog/modelkit 现有 env 导出改为委托 `_with_pool`；gameengine 后台任务句柄按需暴露。

## Phase 2 — 网关仓库接线（消费侧）

- `crates/sdkwork-api-cloud-gateway/src/embedded_dependency_routes.rs`：新增 18 个 `#[cfg(feature = "foundation-*")]` + `workspace_surface_enabled` 装配块，调用 `assemble_api_router_with_pool(pool)`（与已接线 27 个同构，含 `workspace_build_error` 映射）；`EmbeddedDependencyRuntime` 按需扩展（local-router/gameengine 运行时句柄）
- `specs/component.spec.json`：18 个依赖的 `executableExport` 对齐为实际导出名 `sdkwork_api_<code>_assembly::assemble_api_router_with_pool`
- 扩展 `contribution_selection_uses_declared_workspace_ownership` 测试覆盖 18 个 workspace
- `docs/architecture/tech/TECH_ARCHITECTURE.md`：修正 catalog 已嵌入的错误声明，补全集成说明

## Phase 3 — 窄验证

- 每仓库：`pnpm api:assembly:validate` + `cargo check -p sdkwork-api-<code>-assembly`（每批全部通过再进下一批）
- 收尾：`node ../sdkwork-specs/tools/audit-api-assembly-workspace.mjs --workspace ..`；网关仓库 `cargo check --all-features`、`cargo check --no-default-features --features foundation-community`、`cargo test -p sdkwork-api-cloud-gateway`、`cargo fmt -- --check`、`pnpm gateway:api:validate`、`check-process-shared-database-pool.mjs`

## 风险与回滚

- 每个同级仓库独立 commit 可单独回滚；批次内任一仓库 validate/check 失败先修该仓库
- 公共 API 只增不改（新增 `_with_pool`/`assemble_api_router(context)` 导出），不影响各应用现有消费者与 standalone 网关
- 遗留旧式导出的仓库（rtc 等 `assemble_api_router()` env 版）保留不动，仅新增贡献式入口
- 涉及公共 API 变更，符合 AGENTS.md 人工评审条款，本计划即评审确认
