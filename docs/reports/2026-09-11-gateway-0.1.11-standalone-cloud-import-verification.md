## 四、本轮修复的两个构建阻断（真实根因）

### 1. `pnpm -v` 在仓库内报 `[ERROR] disk I/O error` —— 不是 DrvFS 的问题

**现象**：`cd <repo> && pnpm -v` → `[ERROR] disk I/O error`，导致一切经 pnpm 转发的 bin
入口（`bin/docker-image.sh build`）不可用；而 `cd /mnt/e && pnpm -v` 正常。

**根因（本次定案）**：**pnpm 的 `manage-package-manager-versions`**。仓库
`package.json#packageManager` 声明 `pnpm@10.33.0`（工作区 76/77 仓一致），而 WSL 内安装的是
`11.24.0`；版本不一致时 pnpm **在读取任何配置之前**启动版本管理器去拉取目标版本，该路径在
DrvFS 上必失败，于是只打印 `disk I/O error`，且 `pnpm -v` / `pnpm config get` / `pnpm run` 全部不可用。

最小复现（已在实测中确认）：`/mnt/e/<tmp>` 放 `{"name":"probe","packageManager":"pnpm@10.33.0"}`
即复现；删掉 `packageManager` 字段即恢复。

**无效处置**（均实测失败，勿再尝试）：`--config.manage-package-manager-versions=false`、
`npm_config_manage_package_manager_versions=false`、局部 `.npmrc`、`PNPM_HOME=<ext4>`、
`--config.package-manager-strict=false` —— 版本管理器先于配置读取。

**有效修复**：`npm i -g pnpm@10.33.0`（只改 `~/.npm-global`，无需 sudo）。

> 旧备忘"不要在 /mnt/e 上用 pnpm（跨设备硬链接 / `.modules.yaml` storeDir）"是**误判**，
> 已连同 skill `sdkwork-wsl-docker-packaging` 一并更正。

### 2. `cargo metadata --locked` 失败：Cargo.lock 已过期

`Updating git repository …` + `cannot update the lock file … because --locked was passed`。
`--locked` 由 `scripts/build-api-cloud-gateway-container.mjs:329,360` 与 `scripts/package-server.mjs`
强制，而 HEAD 的 `Cargo.lock` 落后于兄弟仓 `sdkwork-agents`
（`crates/sdkwork-agents-runtime-facade` 新增 `jsonschema`）。

修复：无 `--locked` 跑一次 `cargo metadata --no-default-features --features
platform-foundation-suite-container` 刷新锁文件 —— `Locking 6 packages`（`jsonschema` 及其
`fraction`/`referencing`/`roxmltree`/`jsonschema-{regex,value}`），`Cargo.lock +103/-6`。
**该改动需随本轮一起保留**（否则构建再次 `--locked` 失败）。

### 6.3 模块级校验

- **激活期校验**（`serve-imports` 逐模块）：`module_id=sdkwork-api-cloud-gateway` →
  `virtual_hosts=16 upstreams=1 unreachable=0`；五环境 `unreachable>0 / validation errors = 0`
  （每环境 288 条模块校验，dev 因实例默认环境不同为 432 条）。
  > 日志行中 `profile=standalone` 是 webserver 侧 **path-probe 辅助函数**的默认值
  > （§17.3.1 注），实际加载路径是 `nginx.cloud.<env>.conf` —— 非配置错误。
- **layout v3 等价性**：`node sdkwork-specs/tools/webserver/render-nginx-sidecars.mjs
  --workspace=<workspace-root> --module=sdkwork-api-cloud-gateway --validate`
  重渲染 10 个 sidecar（5 env × 2 profile）后 `git status` **无任何改动** ⇒ sidecar 与
  `effective(<profile>.<environment>)` 逐字节等价。
- **工作区审计**：`node sdkwork-specs/tools/webserver/audit-modules.mjs <workspace-root>`
  → `sdkwork-api-cloud-gateway  ok  enabled  topo=yes  surfaces=1  bases=16  hosts=16  envs=ok`。
- **部署态 sidecar 与源码一致**：比对 `/opt/deploy/sdkwork-space/sdkwork-api-cloud-gateway/deployments/webserver/`
  8 个文件，全部 `SAME`。
- **upstream 目标**：cloud 集 `upstream gateway { server sdkwork-api-cloud-gateway:8080; }`；
  非生产 1 个 `server` 块 16 个 `server_name`，生产 16 个 `server` 块（逐域 SNI/TLS）。
  webserver 容器内 `getent hosts sdkwork-api-cloud-gateway` → 侧栈 IP（dev `172.27.0.4`、
  test `172.28.0.3`、staging `172.29.0.3`、demo `172.30.0.3`、prod `172.31.0.3`）。

## 九、遗留与待决策

1. **`Cargo.lock` 未提交**：本轮刷新（`+103/-6`，新增 `jsonschema` 等 6 包）为构建必需，
   与工作区既有的跨仓未提交改动（`sdkwork-agents` 等）一并待提交。
2. **webserver 日志中的 `profile=standalone` 字样**（§6.3）：实际加载 cloud sidecar，
   属 path-probe 默认值输出，但容易误读。若要消除歧义，应在 webserver 侧把"实际加载 profile"
   写进日志（上游仓改动）。
3. **`resolve` 指令未使用**：cloud 集 upstream 直接写 `server sdkwork-api-cloud-gateway:8080;`。
   spec 审计（`audit-modules`）判 `ok`、激活校验 `unreachable=0`，故本轮不视为违规；
   但若后续改为多实例/动态 IP 的容器编排，需按 `NGINX_SPEC.md` 补 `resolve` + resolver。
4. **部署态 space 检出残留备份文件**：
   `/opt/deploy/sdkwork-space/sdkwork-api-cloud-gateway/deployments/webserver/` 下有 5 个
   `*.conf.bak-pre-adaptive-20260905`、`snippets/gateway-locations.nonproduction.conf.bak-pre-adaptive-20260905`。
   部署根不应有散落文件（`APPLICATION_DEPLOY_LAYOUT_SPEC.md §9.1`），建议归入 `archives/`。
5. **历史项**：production cloudrouter 密钥仍为 bundle env 同源的 dev 占位形态；
   staging/prod 缺 `SDKWORK_KNOWLEDGEBASE_OUTBOX_WEBHOOK_URL`（每 10s ERROR，非本轮回归）；
   探测残留库待清理。
